EXISTING TOOL REVIEW

scripts/bench.py provides receive-only serial capture and dated raw .bin,
timestamped-hex .jsonl and metadata .json output. Its inventory and unopened
serial-plan modes do not open the port; running them would create new files,
so they were not run in this assignment.

scripts/console-command.py identifies the known FTDI, requests exclusive access,
opens the port, sends an initial CR, requires a shell-shaped prompt, then sends
the explicit command. It saves RX bytes and RX/TX hex events and closes the
port. A prompt-shaped response is not proof of root; resume with a framed id
check before root-dependent work. No automatic login is implemented.

The helper waits a fixed 0 < wait <= 30 seconds. Its status "command capture
finished" means the receive window ended; it does not verify remote exit status,
completion, payload size, source checksum, or file validity. The displayed
response filters some runtime lines and truncates at 18,000 characters. Neither
display filtering nor .txt output is a backup decoder. Preserve raw data and
parse a separate framed protocol. Long transfers can outlast the helper even
though its host exit is successful. No helper changes are made by this plan.

UART FILE TRANSFER DESIGN AND RATE BUDGET

115200 8N1 uses 1 start + 8 data + 1 stop bit per character: 115200/10 =
11,520 serial payload bytes/s, about 11.25 KiB/s per direction, before console
noise, framing, retries, command overhead or host handling. It is not 115,200
bytes/s. Base64's 4/3 expansion reduces the ideal original-file rate to about
8,640 bytes/s (8.44 KiB/s), lower again with line breaks/frame headers.
Hex is at most 5,760 original bytes/s before framing. The 24,233-byte idle
capture (~404 B/s average) measures unsolicited output, not transfer capacity.

For rough planning only, use 2-6 KiB/s original-file throughput after encoding
and overhead until measured with a verified small transfer. A 64 KiB file would
take roughly 11-33 s of payload time at that assumed rate, plus setup/checks.
A 1 GiB base64 transfer has a theoretical minimum of about 34.5 hours even with
zero noise or retries; at the provisional 2-6 KiB/s it would take about 49-146
hours. Bulk UART imaging is therefore excluded.

Use a strict, unique nonce per transfer and unambiguous line-framed records:
BEGIN with logical source path/length/encoding/checksum algorithm; numbered
DATA records with offset, decoded length, encoded payload and source-computed
chunk checksum where supported; END with total bytes, whole-file checksum and
individual command status. Validate complete marker lines, not substrings in
the echoed shell command. Preserve raw RX/TX so transport corruption is auditable.

Choose 1-4 KiB decoded chunks and an ASCII-safe encoding supported by existing
tools. The device need not write a staging file: read an allowlisted regular
file by bounded ranges and stream encoded output. Compute source size and
checksum before and after; the host decodes strictly, verifies exact contiguous
offsets/sequence/length, then matches the whole-file checksum. With a static
source and whole-file checksum only, a mismatch requires retry of the complete
small file; do not advertise chunk verification/resume without chunk checksums.
Never treat stripped log lines or guessed missing bytes as verified content.

Console logs can interleave at byte boundaries, including inside payloads or
echoed commands. Reject damaged frames; retry at most two times with a smaller
chunk or stop and defer. Do not disable logging or kill services to quiet it.
If existing tools cannot safely encode/checksum within the budget, record the
limitation and defer. Do not upload binaries or install packages as a workaround.
Dynamic /proc records are observations, not stable file backups; timestamp each
capture and do not require equal pre/post hashes of changing live state.

The host runner should wait for an authenticated, nonce-matched end record and
prompt, not a fixed sleep. Give every operation an output cap and deadline. On
timeout save partial evidence and mark command state unknown; do not issue a
new command until the owner safely reestablishes a shell prompt. A serial close
does not necessarily stop the remote command. Do not use blind Ctrl-C or kill
broad process classes. Existing 30 s capture-window behavior needs to be
accounted for before choosing even a 64 KiB UART file.

BOOT-CRITICAL AND DEVICE-UNIQUE BACKUP CANDIDATES

These are discovery categories, not claims about this CMU's exact layout.
For each, record actual source path/device, physical versus logical layer,
size/geometry, filesystem, read/write state, firmware binding and capture method.

- Boot chain: bootloader(s), environment, boot configuration, partition/layout
  descriptors, kernel and any device tree/initramfs, root filesystem, startup/
  mount scripts, failsafe/recovery partitions and update metadata. Include
  NOR/SPI or auxiliary-controller firmware only if actually identified.
- Device identity/configuration: FGSN (present in login banner), factory serial/
  part numbers, region/hardware variant, calibration and manufacturing records,
  persistent NVRAM/config stores, VIN/pairing/coding if present, cryptographic
  identities/certificates/keys and licenses if present. Do not infer exact paths
  or export secret contents before the relevant store is mapped and reviewed.
- User/feature state: persistent settings, paired-device/config databases,
  navigation/SD entitlements and USB/media configuration. Observe existing
  USB/SD device and mount state; do not write to, reformat or repurpose SD/USB.
- External state: navigation SD and other controllers may contain data outside
  the CMU filesystem. A CMU file archive cannot claim to cover these. No
  auxiliary controller EEPROM or OTP probing is proposed before Ethernet.

NAND uses proprietary FlashFX/relfs per the supplied constraint, so distinguish
filesystem-level files, the FlashFX logical export, and physical NAND pages
including bad-block/ECC/OOB metadata. A device-node dd read may capture only a
translated logical view, omit necessary metadata, or give inconsistent live
filesystem content. A hash proves byte stability of an acquired artifact; it
does not prove a valid restore procedure or suitability for another unit.
Do not provide a generic dd restore command, remount filesystems, stop the
application stack, freeze storage, use NAND utilities, or invoke vendor
reflash/reset scripts in this interim scope.

A later recovery study must identify boot media/layout, exact FlashFX/relfs
representation and tooling, factory/device-unique dependencies, consistency
method and a recovery path compatible with that representation. Until a
separately authorized representative restore succeeds, label any future bulk
artifact "unvalidated acquisition", specifying layer and consistency limits.
Never label a raw dd dump "tested recovery" or imply this plan created one.

  hardware exists and B+/ACC behavior/shutdown timing are understood. Relay
